# 국내 신입 게임 클라이언트 포트폴리오 조사

조사일: 2026-10-06. 최적화를 시작하기 전 참고자료와 실험 방향을 정리한 문서다. 최종 지원용 원고나 합격 보장 기준이 아니다. 한국어 발표, 기업이 게시한 신입 채용 요건, 작성자가 공개한 DX11 포트폴리오를 구분해서 읽었다. 몇 개의 사례로 국내 채용 전체의 빈도나 합격선을 추정하지 않는다.

## 1. 먼저 읽을 한국어 자료

### 신입 채용을 평가하는 관점

[윤석주 — 신입 게임 프로그래머가 되는법, NDC2019](https://ndcreplay.nexon.com/NDC2019/sessions/NDC2019_0053.html)

[발표 슬라이드 — devCAT Studio, NEXON 업로드](https://www.slideshare.net/slideshow/ndc2019-142896444/142896444)

슬라이드 18~29에서는 프로젝트 경험과 의사 결정, 연구 과정과 결과, 본인 기여와 코딩 스타일을 설명한다. 영상에 해당 구현 코드 위치를 연결하고 시행착오도 보여주는 구성을 권한다. 31~45에서는 알고리즘 문제 해결과 언어·그래픽스·메모리·자료구조 등 기본 지식을 다룬다.

이 발표는 2019년 넥슨 채용 경험을 토대로 한 발표자 개인의 분석이다. 현재 회사의 공식 채용 기준이나 모든 회사의 절차로 해석하지 않는다. 우리에게 참고할 것은 결과물, 본인 작업, 의사 결정 근거를 읽기 쉽게 연결하는 방식이다. 코딩 테스트와 기술 면접 준비도 별도로 필요하다.

### 그래픽스를 공부하는 신입에게 요구되는 깊이

[기현우 — 뉴비탈출 넘버원: 그래픽스 프로그래밍 길들이기, NDC2014](https://ndcreplay.nexon.com/NDC2014/sessions/NDC2014_0096.html)

공식 페이지에 발표 전사가 있다. API 예제를 따라 쓰는 데 그치지 않고 프로젝트의 목표에 맞게 수정하는 능력, C++·수학·그래픽스 이론을 함께 공부하는 방향을 강조한다. 오래된 커리어 발표이므로 당시 기술 사례를 현재 필수 기술 목록으로 옮기지 않는다.

우리 프로젝트에서는 배칭 API를 호출하는 것에 더해, 왜 제출 비용이 줄어드는지와 어떤 합성 순서를 보존해야 하는지를 설명하는 공부로 연결한다. Software Rasterizer 등 발표의 학습 제안을 현재 게임의 필수 구현으로 추가하지 않는다.

### 기업이 명시한 신입 채용 요건

[스타라이크 — 클라이언트 프로그래머 신입](https://www.wanted.co.kr/wd/269095)

확인 시점에는 마감된 공고다. 언어 활용, 자료구조·알고리즘 이해, 커뮤니케이션을 명시한다. 채용 중인 자리 소개가 아니라 신입 평가 항목의 실제 예시로 사용한다.

[이스트게임즈 — MMORPG 클라이언트/모바일 RTS 서버 공고](https://lab.incruit.com/jobs/2608240000078)

2026-08-24 시작으로 표시된 기업 공고의 MMORPG 클라이언트 항목에서 신입 지원 범위와 C++ 프로젝트 수행, 운영체제 구조 이해, 게임 그래픽스 지식, 포트폴리오 제출을 확인했다. 같은 페이지의 서버 요건과 다른 프로젝트 요건을 클라이언트 신입 공통 기준에 섞지 않는다. 모집 상태는 지원 시 다시 확인한다.

### 실제 한국어 DX11 포트폴리오 구성

[원택 — 스폰지밥 게임 모작: 3D 액션 어드벤처 게임](https://1-taek-gameprogramming.tistory.com/59)

2022년 공개한 C++/DX11 작업이다. 시연 영상과 콘텐츠 동작을 보여주고 기술 항목에서 스킨드 인스턴싱의 데이터 배치, 카메라의 내적·외적 활용 등을 설명한다. 기능 이름에 실제 구현 원리를 연결하는 구성을 참고할 수 있다.

작성자의 신입 여부나 합격 결과는 이 글로 확인하지 않았다. 기술의 개수·제작 기간·스킨드 인스턴싱을 신입 합격선으로 삼지 않는다. 우리 최적화 사례에는 추가로 같은 조건의 전후 측정과 변경 코드 링크를 붙인다.

## 2. 요구 역량과 우리 프로젝트에서 보여줄 증거

아래 구체 질문과 실험은 위 자료를 바탕으로 정리한 우리 프로젝트의 학습 제안이다. 기업 공고에 모두 적혀 있다는 뜻은 아니다.

| 역량 | 우리 게임에서 제시할 근거 | 스스로 설명할 질문 |
|---|---|---|
| C++와 메모리 수명 | BulletSystem의 저장 방식, 리소스 캐시와 ComPtr 소유권 | vector 재할당은 어떤 참조를 무효화하는가? 풀은 무엇을 재사용하는가? |
| 자료구조와 알고리즘 | 빈 슬롯 탐색, 활성 목록, Uniform Grid의 비교 | 생성·제거·전체 순회의 비용이 각각 어떻게 달라지는가? |
| 그래픽스와 수학 | 좌표 변환, 시트 UV, 블렌딩, 상수 버퍼와 렌더 제출 | 크기/회전 순서가 왜 중요한가? CPU가 GPU에 어떤 데이터를 전달하는가? |
| 문제 재현과 검증 | 반복 가능한 탄막 장면, 구간 측정, 변경 전후 검사 | 병목이라는 근거는 무엇인가? 측정 오차와 대기시간은 어떻게 구분했는가? |
| 설계와 설명 | GameScene/Graphics/HUD/캐시의 책임 | 누가 데이터를 소유하고 누가 변경하는가? 분리 덕분에 어떤 변경이 쉬워졌는가? |

현재 프로젝트의 강점은 C++/Win32/DX11에서 입력부터 게임 진행과 표시까지 연결한 경험이다. 3D 카메라·투영·조명·스키닝이나 Unreal 프로젝트 경험은 현재 2D 결과물만으로 입증되지 않는다. 지원할 직무가 이를 요구한다면 별도 학습과 결과물이 필요하다. 개인 프로젝트로 팀 협업 경험까지 주장하지 않는다.

## 3. 최적화 포트폴리오의 중심 사례

잠정 주제: **C++/DirectX 11 탄막 게임에서 대량 탄환의 비용을 측정하고, 같은 동작과 표현을 유지하면서 처리 한계를 확장한 과정**.

극한 부하 실험은 유지한다. 다만 탄수 자체와 필수 구현 기술을 미리 목표로 고정하지 않는다. 신입으로서 강조할 것은 문제를 재현하고 원인을 찾고, 기본기에 근거해 변경한 뒤 결과를 검증하는 능력이다.

### 사례 A — 개별 스프라이트 렌더 제출에서 묶음 처리로

- 현재 활성탄은 후광과 몸체를 각각 DrawSprite로 그린다. Graphics의 개별 경로는 변환/Tint 버퍼를 따로 Map하고 DrawIndexed를 호출한다.
- 조사할 것: 호출 횟수, 렌더 제출 CPU 시간, GPU 시간, 해상도와 후광에 따른 변화.
- 후보: 중복 상태 변경 제거, 데이터 업로드 묶기, 배칭/인스턴싱. 어느 순서가 유리한지는 측정 후 결정한다.
- 학습 핵심: 공유 기하와 개별 데이터, CPU→GPU 전송, 상태별 묶음, Alpha/Additive 합성 순서.
- 자료 구성: 같은 장면의 전후 영상 → 호출 구조 → 측정 → 변경 코드 → 시간과 품질 비교.

### 사례 B — 탄환의 생성과 순회 자료구조

- 현재 생성은 빈 슬롯을 선형 탐색한다. 8192 용량에는 비활성 슬롯도 존재한다.
- 조사할 것: 발사량과 활성 비율에 따른 생성/업데이트/제거/카운트 비용을 분리한다.
- 후보: 빈 인덱스 스택과 활성 인덱스 목록. 변경 시 중복 반환, 삭제 중 순회, 인덱스 유효성도 검증한다.
- 학습 핵심: 시간 복잡도와 실제 측정의 차이, 연속 메모리, 수명과 식별자, 자료구조 유지 비용.
- 자료 구성: 선택한 구조의 그림 → 연산별 비용 → 같은 탄막의 측정 → 유지해야 할 불변식과 검증.

### 사례 C — Uniform Grid를 언제 쓰는가

- 후보 충돌 검사 감소와 Grid 구축·조회 비용을 합쳐 비교한다.
- 적은 탄, 균등 분포, 밀집 탄 등 다른 조건도 조사한다. 빠른 탄의 터널링은 별도 정확성 한계이며 Grid 최적화가 해결했다고 쓰지 않는다.
- 기존 소규모 벤치마크에서는 적은 탄에서 전체 순회가 더 빨랐다. 이 결과를 현재 8192 풀의 전체 게임 성능으로 확대 해석하지 않는다.
- 학습 핵심: 알고리즘의 전제 조건, 상수 비용, 공간 분포, broad phase와 실제 판정의 구분.
- 자료 구성: 후보 수 + 구성/조회 시간 + 전체 충돌 시간 → 유리/불리한 조건 → 채택 이유.

이 세 사례 모두 개선 성과가 아직 확정되지 않았다. 첫 프로파일링 결과에 따라 순서를 바꾸거나 효과 없는 후보를 기각할 수 있다. SIMD·멀티스레드·GPU 시뮬레이션은 후속 병목과 학습 필요가 확인될 때 검토한다.

## 4. 최적화 전에 기록할 자료

1. BGM 등 현재 작업 트리를 포함하는 정확한 기준 커밋.
2. 실제 최종보스 장면과 별도 스트레스 장면의 동일 입력/스폰 조건.
3. 장비·해상도·Release 설정·VSync·워밍업·측정 구간.
4. 활성 탄수, 스폰 요청/누락, CPU 구간 시간, GPU 시간, 프레임시간 원자료.
5. 변경별 가설, 채택/기각 이유, 코드 차이, 동작/화질 검사, 남은 한계.

현재 풀 용량8192와 자동 검사 최대 활성탄3230은 성능 합격 수치가 아니다. 함수 시간 감소와 전체 프레임 개선을 따로 기록한다. FPS만 표시하지 않고 ms와 여러 실행의 변동도 남긴다.

## 5. 추후 지원 자료의 읽는 순서

게임 소개와 짧은 시연 → 사용 기술·작업 범위 → 대표 사례 2~3개 → 코드 위치와 재현 방법 → 측정 환경·원자료 → 한계.

각 사례는 문제 → 근거 → 대안과 선택 이유 → 구현 → 검증 → 한계로 구성한다. 전후 표는 측정 후 채운다. 에이전트가 구현한 주변 코드와 본인이 직접 구현·분석·검증한 작업을 구분하고, 대표 사례의 코드는 스스로 수정하고 설명할 수 있는 수준까지 학습한다. 문서에 적은 기능을 본인이 전부 독립 구현했다고 표현하지 않는다.

다음 Step은 측정 기준 장면 준비다. 이번 조사에서 게임 코드, 최적화 알고리즘, 성능 결과는 변경하지 않았다.
