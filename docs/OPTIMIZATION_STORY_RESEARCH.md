# 최적화 사례 조사와 Danmaku Lab 실험 구성

2026-10-06. 현재 게임을 최적화 전 출발점으로 삼는다는 사용자 요청에 따른 사전 조사다. 최종 포트폴리오 원고나 성능 결과가 아니며 이번 작업에서는 최적화 코드를 변경하지 않았다.

후속 사용자 요청에 따라 국내 신입 관점의 우선 자료를 [한국어 신입 포트폴리오 조사](JUNIOR_PORTFOLIO_RESEARCH_KO.md)에 정리했다. 아래 해외 사례는 실험과 문서 구성의 보조 참고로 유지한다. 국내 신입 요구 역량이나 합격 기준의 근거로 사용하지 않는다.

## 먼저 읽을 사례

### 1. 개인 기술 포트폴리오: 결과를 먼저 보여주고 진단으로 설명

[Kilian Allaire — Paint-on-Texture GPU Optimization](https://kilianallaire.com/paint-optim.html)

Unity/D3D12 기반 페인팅 기능을 다룬 본인 기술 사례다. 첫 화면에 결과와 실행 환경을 배치하고, 증상→프로파일러 캡처→원인→가설별 채택/기각→수정→전후 결과→회고로 이어진다. 에디터 지표와 standalone 빌드 지표를 따로 표시하고 작업량 제한에 따른 입력 지연도 설명한다.

참고할 것은 문서 구조다. 작성자의 수치는 독립 검증된 결과로 취급하지 않으며 CPU 대기시간을 GPU 실행시간으로 옮겨 적지 않는다. 해당 페이지의 일반화된 원인 판단을 우리 DX11에 그대로 적용하지 않는다. 우리 자료에서도 결과 요약, 같은 장면의 캡처, 채택/기각 이유, 시각·입력 영향이 연결되어야 한다.

### 2. 실제 스튜디오: 인스턴싱 이후에도 병목을 다시 찾기

[Funovus — Profiling Game Performance](https://www.funovus.com/blogs/profiling-game-performance/)

Wild Castle은 이미 인스턴싱 렌더러를 사용했다. 패스를 끄는 실험으로 비용을 분리한 뒤, 윤곽선이 없는 유닛도 윤곽선 패스에서 처리하는 낭비를 발견했다. 별도의 CPU 조사에서는 사용하지 않는 효과까지 순회하는 구조를 발견했다. 글은 화면에 안 보이는 작업과 실제 필요한 작업을 구분하고, 수정 전 효과를 비활성화해 얻는 이득으로 우선순위를 판단한다.

우리에게는 후광만 끄기/탄환 렌더만 끄기/렌더를 유지한 충돌 비교처럼 비용을 분리하는 실험 방식이 유용하다. 이런 비활성화 결과는 진단 근거이며 최종 품질을 유지한 최적화 성과와 별도로 기록한다. 인스턴싱 도입만으로 조사를 끝내지 않는다.

### 3. 2D 스프라이트 게임: 투명한 픽셀과 오버드로를 보여주기

[Factorio FFF #281 — For a Few Frames More](https://www.factorio.com/blog/post/fff-281)

개발자는 오버드로 시각화에서 거의 보이지 않는 연기가 넓은 영역을 차지하는 이유를 추적했다. 수명이 끝났지만 드문 업데이트 때문에 제거되지 않은 파티클이 여전히 렌더되고 있었다. 같은 글은 포탑 범위 표시에서 여러 대안을 비교하며 어떤 최적화가 특정 확대 조건에서만 유리한지도 설명한다. 벤치마크에는 장면·GPU·해상도·GPU 시간 측정 조건을 함께 적는다.

우리 후광은 몸체보다 큰 사각형으로 겹쳐 그린다. 제출 비용을 낮춰도 GPU 픽셀 비용이 남을 수 있다는 조사 방향에 잘 맞는다. 후광 크기/겹침/해상도를 바꿔 비용 원인을 확인할 수 있다. 반해상도 효과나 외곽 영역 축소는 화질과 합성 결과가 달라질 수 있으므로 동일 품질 개선과 별도 품질 타협으로 구분한다.

### 4. 같은 개발팀의 CPU 사례: 자료구조보다 불필요한 작업부터

[Factorio FFF #421 — Optimizations 2.0](https://www.factorio.com/blog/post/fff-421)

로보포트가 대부분의 시간에 할 일이 없는데도 계속 갱신되는 문제를 찾아, 필요할 때 활성화하는 방식으로 변경했다. 레이더 관련 기능에서는 겹치는 영역을 매번 따로 처리하는 대신 공통 등록 구조를 사용한다. 글은 특정 기능의 시간 감소와 전체 게임의 개선을 따로 표현한다.

우리도 빈 슬롯까지 훑는 비용, 생성할 때마다 빈 슬롯을 찾는 비용, Grid 구성 비용을 각각 측정한다. free index/활성 목록/데이터 분리 등을 검토하되 처음부터 ECS·멀티스레드·SIMD를 목표로 정하지 않는다. 일부 함수가 빨라져도 프레임 전체가 같은 비율로 빨라지는 것은 아니다.

## 우리 게임의 이야기 중심

잠정 주제: **동일한 탄막과 후광을 유지하면서 DX11 탄막 게임의 처리 한계를 높인 과정**.

1. 플레이 가능한3스테이지 게임에서 최종보스의 대량 탄막 요구가 생겼다.
2. 기존 개별 스프라이트 경로로 콘텐츠를 구현하고 재현 가능한 기준 장면을 확보한다.
3. 실제 프레임에서 CPU 업데이트/충돌/렌더 제출/GPU/Present 대기를 분리해 가장 큰 비용을 찾는다.
4. 한 번에 한 가설을 실험하고, 효과와 정확성 검사를 통과한 변경만 비교 대상으로 남긴다.
5. 개선 뒤 다시 측정하여 남은 병목과 처리 가능한 탄수의 변화, 실패하는 조건까지 기록한다.

극한의 기준은 탄수를 크게 적는 것보다 **고정된 장비·화질·시간 예산에서 처리 가능한 부하의 한계**다. 현재 용량8192는 처리 가능한 활성탄 성능 수치가 아니다.24초 충돌 제외 패턴 검사의 최대3230발/누락0도 성능 결과가 아니다.

## 현재 코드로 확인된 사실과 조사 후보

| 확인된 구현 | 후보 실험 | 성과 인정 조건 |
|---|---|---|
| 활성탄마다 후광·몸체 각각 DrawSprite | 상태 변경 중복 제거, 업로드 묶기, 배칭/인스턴싱 비교 | 같은 탄수·시각 결과에서 렌더 제출 시간과 전체 프레임 개선 |
| DrawSprite마다 변환/Tint 상수 버퍼 각각 Map/Unmap | 업로드 횟수·바이트 계측 후 인스턴스 데이터 전송 검토 | 호출 수 감소와 CPU 시간 변화, GPU 시간도 별도 확인 |
| 후광은 각 축+16의 사각형, Additive 합성 | 후광 비활성화 및 크기·해상도 진단, 픽셀 비용 조사 | 화질 유지 여부 표시, 몸체 Alpha/후광 순서 보존 |
| 탄환 생성은 선형 빈 슬롯 탐색, 여러 경로가8192슬롯 순회 | 생성·업데이트·제거·HUD 카운트 비용 분리, free index/활성 목록 검토 | 동일 스폰/제거/충돌/Graze 결과, 누락 증가 없음 |
| Grid는 매 업데이트 Clear/Insert 후 주변 조회 | 전체 순회 대비 구성+조회 총비용과 탄막 분포 비교 | 후보 수뿐 아니라 실제 시간, 적은 탄/밀집 탄에서 역효과 기록 |

위 항목은 코드에서 확인한 호출 형태이며 측정으로 확정된 병목이 아니다.3230발이 동시에 그려지는 프레임이면 탄환 부분만6460 DrawIndexed/12920 Map 호출이 발생한다는 것은 코드상 계산이며 실제 캡처 수치는 아직 없다. 배경·캐릭터·HUD 호출은 별도다.

## 최적화 시작 전에 확보할 증거

- 현재 소스/자산을 정확한 커밋으로 고정한다.968bbac 이후 BGM 변경은 아직 미커밋이므로 기준 커밋과 작업 트리를 혼동하지 않는다.
- 일반 플레이 장면과 반복 가능한 최종보스 장면을 분리한다. 테스트용 무적/보스 HP 고정 등을 추가한다면 전후 동일 정책으로 사용하고 기록한다. 아직 이런 측정 모드는 구현하지 않았다.
- 측정은 동일 Release 설정/해상도/장비/드라이버/후광 설정으로 한다. 첫 리소스 로딩·워밍업은 정상 상태 측정과 분리하고, VSync/FPS 제한/디버그 레이어 정책을 기록한다.
- 같은 플레이 시간 구간/입력·패턴/활성탄 분포에서 여러 번 측정하고, 평균 및 p95/p99 프레임시간과 시간 그래프를 저장한다. Present 대기와 GPU 실제 실행시간을 혼동하지 않는다.60Hz 업데이트1회 비용과 렌더 프레임 비용도 구분한다.
- 실제 장면과 별도 스트레스 장면에서 부하를 단계적으로 올려 성능 곡선을 만든다.8192보다 큰 실험은 별도 용량 설정으로 구분하며 실제 게임에 필요한 수치와 합성 한계를 섞지 않는다.
- 전후 영상/캡처·스폰 요청/누락·명중/점수/Graze·사망/단계 진행을 확인한다. Additive/Alpha 합성 순서를 바꾸는 배칭은 시각 정확성을 따로 검사한다.
- 개선 하나마다 코드 커밋, 원자료 CSV, 캡처, 측정 환경, 기각한 가설과 비용을 남긴다. 문서의 결과 표는 측정 뒤 채운다.

## 나중에 포트폴리오 한 사례를 구성할 틀

결과 요약/전후 영상 → 실제 게임 요구 → 재현 장면·실행 환경 → 기준 캡처 → 원인 가설·분리 실험 → 선택한 구현·대안 → 전후 프레임시간·구간별 비용·부하 곡선 → 동작/품질 검증 → 한계·기각한 시도·다음 병목.

대표 결과3~4개를 본문에 깊게 쓰고 나머지는 실험 기록으로 연결한다. 기술 이름의 개수나 목표 배수를 먼저 정하지 않는다. GPU 시뮬레이션 같은 구조 변경은 CPU의 판정/읽기 동기화까지 실제 병목으로 확인된 경우에 검토한다.
